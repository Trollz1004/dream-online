## 1. Which MCP SDK version `ops/kit/server.mjs` uses and whether it supports tasks

`ops/kit/server.mjs` uses no MCP SDK at all (version: none). Line 2 of `ops/kit/server.mjs` states `// Starter Kit MCP JSON-RPC 2.0 stdio server (dependency-free Node ESM).` and lines 5-10 import only Node built-ins (`node:fs`, `node:os`, `node:path`, `node:readline`, `node:url`) plus `../fleet/fleet-map.mjs`. The repository's `package.json` (lines 20-46) declares zero `@modelcontextprotocol/*` packages.

In `handleJsonRpcMessage` (`ops/kit/server.mjs` lines 601-667), `initialize` (lines 619-628) returns `protocolVersion: params.protocolVersion || '2025-06-18'` and `capabilities: { tools: {} }` with no task capability or extension declaration, `tools/call` (lines 633-659) always returns a synchronous `content: [{ type: 'text', text }]` payload, and any `tasks/*` method falls through to `default:` (lines 660-665) and returns JSON-RPC error `-32601` (`Method not found`).

Even if `@modelcontextprotocol/sdk` were imported from the version already installed in sibling packages on the Alienware (`1.32.1`, found in `%USERPROFILE%\DesktopCommanderMCP\package.json` line 94 and `%USERPROFILE%\antigravity\ANTIGRAVITY-wt-pr335\services\mission-mcp\node_modules\@modelcontextprotocol\sdk\package.json` line 3), `@modelcontextprotocol/sdk` `1.32.1` only includes the older `2025-11-25` experimental task draft under `dist/esm/experimental/tasks/` (`server.d.ts` lines 138-169 and `interfaces.d.ts` lines 43-47, 162-226, which use `tasks/get`, `tasks/result`, `tasks/list`, and `tasks/cancel`). ## 2. What would have to be added to `ops/kit/server.mjs` for `queue_ticket`

To let `ops/kit/server.mjs` queue a kitchen ticket and hand back a task handle that completes when the ticket lands in `done\` or `failed\` with the PR link as the result, five additions are required in `ops/kit/server.mjs`:

- **Capability negotiation (`ops/kit/server.mjs` lines 619-628 and 633-659):** Advertise `io.modelcontextprotocol/tasks` support during discovery (`initialize` / `server/discover`) and check per-request client opt-in under `params._meta["io.modelcontextprotocol/clientCapabilities"].extensions["io.modelcontextprotocol/tasks"]` (per `modelcontextprotocol.io/extensions/tasks/overview` and `modelcontextprotocol/ext-tasks` `specification/draft/`). If a client invokes a task-only path without declaring `io.modelcontextprotocol/tasks` support, return JSON-RPC error `-32021` (missing required client capability, `modelcontextprotocol/ext-tasks` `schema/draft/schema.ts`).
- **Tool definition and ticket writer (`ops/kit/server.mjs` lines 45-112, 114-127, 580-599):** Add `queue_ticket` to `KIT_TOOLS` (lines 45-112) with inputs `id` (validated with `validateSafeToken` at line 140 against `SAFE_NAME_RE` at line 30), `title`, `body`, and optional `lane`, `model`, `repo`, and `base` headers matching the format in `ops/router/INBOX.md` lines 28-47. Scan `title` and `body` with `findSecretRule` (`ops/kit/server.mjs` lines 32-43, 166-174) so secrets, `.env` references, literal user folder paths, vault paths, and loopback reach URLs are refused before disk write. Resolve `inboxDir` in `resolvePaths` (`ops/kit/server.mjs` lines 114-127) to `%USERPROFILE%\antigravity\.fable-kitchen\inbox` (matching `DEFAULT_INBOX_DIR` in `ops/router/inbox-runner.ts` line 123), write `%USERPROFILE%\antigravity\.fable-kitchen\inbox\queued\<id>.md` as UTF-8 with no BOM (`%USERPROFILE%\antigravity\.fable-kitchen\orders\RULES.md` line 6), and return a `CreateTaskResult` from `tools/call` containing `resultType: "task"`, `taskId` (matching or mapping to `<id>`), `status: "working"`, `statusMessage: "queued"`, `pollIntervalMs: 15000`, and `ttlMs: 86400000`.
- **The three task RPC methods in `handleJsonRpcMessage` (`ops/kit/server.mjs` lines 618-666):**
  - `tasks/get`: Accepts `{ taskId }`. Looks up the ticket across the inbox folders defined in `ops/router/inbox-runner.ts` lines 187 and 333-339 (`queued`, `running`, `done`, `failed`, `for-judge`). While `<id>.md` is in `queued\` or `running\`, it returns `status: "working"` with `statusMessage` set to `"queued"` or `"running"`. If `<id>.md` is parked in `for-judge\` (`ops/router/inbox-runner.ts` lines 2357-2366; `ops/router/INBOX.md` line 16), it returns `status: "input_required"` with `inputRequests` describing the judge gate. When `<id>.md` lands in `done\` (`ops/router/inbox-runner.ts` lines 2768-2772), it reads `%USERPROFILE%\antigravity\.fable-kitchen\inbox\done\<id>.log`, extracts the GitHub PR link using `GITHUB_PR_URL_REGEX` (`/https:\/\/github\.com\/[A-Za-z0-9_.-]+\/[A-Za-z0-9_.-]+\/pull\/\d+/i` from `ops/router/adapters/types.ts` lines 10-11, which `inbox-runner.ts` checks at lines 2580 and 2720-2721), redacts the output with `redactOutput` (`ops/kit/server.mjs` line 129), and returns `status: "completed"` carrying the final tool result (`content: [{ type: "text", text: prUrl }]`). When `<id>.md` lands in `failed\` (`ops/router/inbox-runner.ts` lines 1502-1505, 1989-1993, 2304-2312, 2777-2782), it reads `%USERPROFILE%\antigravity\.fable-kitchen\inbox\failed\<id>.log` and returns `status: "failed"` with the failure reason from the log (and any partial PR link if one was opened before failure).
  - `tasks/update`: Accepts `{ taskId, inputResponses }` (`modelcontextprotocol.io/extensions/tasks/overview` and `modelcontextprotocol/ext-tasks`). When a task is in `status: "input_required"` (for example, parked in `for-judge\` or waiting on a human answer), it applies the client's response, moves or updates the ticket back into `queued\` when appropriate, transitions the task back to `working`, and returns an empty result `{}`.
  - `tasks/cancel`: Accepts `{ taskId }` (`modelcontextprotocol.io/extensions/tasks/overview` and `modelcontextprotocol/ext-tasks`). Implements cooperative cancellation: if `<id>.md` is still in `queued\`, it removes the file from `queued\` into a cancelled archive folder (not `failed\`, so it does not trip the runner's `MAX_CONSECUTIVE_FAILURES = 3` stop at `ops/router/inbox-runner.ts` lines 138 and 2034-2055), marks the task record `status: "cancelled"`, and returns `{}`. If `<id>.md` is already in `running\`, `done\`, or `failed\`, `ops/router/inbox-runner.ts` owns the child `agy` process, so `tasks/cancel` returns `{}` and lets the task settle according to cooperative cancellation semantics.
- **The five task statuses (`modelcontextprotocol.io/extensions/tasks/overview` and `modelcontextprotocol/ext-tasks`):**
  - `working` (non-terminal: ticket is in `inbox\queued\` or `inbox\running\`).
  - `input_required` (non-terminal: paused waiting for client input via `tasks/update`, such as a ticket parked in `inbox\for-judge\`).
  - `completed` (terminal: ticket is in `inbox\done\<id>.md` and its PR URL has been extracted from `inbox\done\<id>.log`).
  - `failed` (terminal: ticket is in `inbox\failed\<id>.md` with the failure log in `inbox\failed\<id>.log`).
  - `cancelled` (terminal: ticket was removed from `inbox\queued\` via `tasks/cancel` before execution finished).
- **Where task IDs are stored to survive a restart:**
  - Store the task index in `%USERPROFILE%\antigravity\.fable-kitchen\inbox\mcp-tasks.json` (or `%USERPROFILE%\antigravity\.fable-kitchen\memory\kit-tasks.json`, beside `%USERPROFILE%\antigravity\.fable-kitchen\memory\kit-memory.jsonl` at `ops/kit/server.mjs` line 124 and `%USERPROFILE%\antigravity\.fable-kitchen\routines-state.json` at `ops/router/INBOX.md` line 95), written atomically on every state change with `{ taskId, ticketId, repo, createdAt, ttlMs, pollIntervalMs, status, statusMessage, prUrl }`. Because `%USERPROFILE%\antigravity\.fable-kitchen\inbox\{queued,running,done,failed,for-judge}\<id>.md` and `<id>.log` already persist on disk across process and machine restarts (`ops/router/inbox-runner.ts` lines 333-339), mapping `taskId` deterministically to `<id>` also lets `tasks/get` recover the state directly from the inbox folders even if the JSON state file is cold.

## 5. Size estimate in lane hours and the one thing most likely to go wrong

- **Size estimate:** **1 to 1.5 lane hours** (one executor ticket touching `ops/kit/server.mjs` and `ops/kit/server.test.mjs`, roughly 180 to 220 lines of dependency-free Node ESM plus unit tests) to add `queue_ticket`, `tasks/get`, `tasks/update`, `tasks/cancel`, and persistent task state in `%USERPROFILE%\antigravity\.fable-kitchen\inbox\mcp-tasks.json` for local MCP clients on the Alienware (such as signed-in `Claude Code`). Exposing that server to a cloud `claude.ai` session is not a kit-server code task and is blocked without a remote MCP transport route to the Alienware (which the ticket rules forbid adding via new ports, tunnels, or accounts).
- **The one thing most likely to go wrong:** **False failure or premature timeout during the wheel's single automatic re-queue and quota-fallback window (or inability of `claude.ai` to poll the local stdio server at all).** In `ops/router/inbox-runner.ts` (lines 2026, 2650, 2717-2737; `ops/router/INBOX.md` lines 52-53), a ticket that hits a quota/429 error, a missing PR on the first pass, or a 10-minute liveness timeout is moved back to `queued\` and re-run once before landing in `done\` or `failed\`, and each lane attempt can run up to 20 minutes (`%USERPROFILE%\antigravity\.fable-kitchen\orders\RULES.md` line 7). If `tasks/get` reports a failure before `<id>.md` actually lands in `inbox\done\` or `inbox\failed\`, or if `ttlMs` / the client's polling window is shorter than a two-attempt wheel cycle (up to 40 minutes plus queue wait behind older tickets in `queued\`), the caller will mark the MCP task failed or expired while the wheel is still finishing the retry and opening the pull request.
